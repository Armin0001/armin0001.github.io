How I Build Working with LLMs

The model writes the first draft. I own everything around it.

I treat an LLM the way I’d treat any powerful, unreliable component: give it precise inputs, constrain what it can do, and measure what comes out. The typing was never the hard part. The spec, the context and the proof are, and those stay with me.

The loop

Every piece of AI-assisted work I do goes through the same five steps. The model is in the middle three. I’m in all five.

  1. Frame

    Before there is a prompt, I write down what done looks like: the outcome, the constraints, what is out of scope, and how the result will be checked. A vague brief gets you confident nonsense, faster.

  2. Feed

    Then I assemble what the model cannot guess: the source-of-truth documents, the existing code and its conventions, an example of good. If two sources disagree, that gets settled before the model has to choose.

  3. Plan

    For anything non-trivial the model proposes an approach first, and I push on it. A plan is cheap to change. A diff is not.

  4. Build in small steps

    Changes land in pieces small enough to read. Each piece comes with a check: a type check, a test, a script, a rendered page.

  5. Verify, then review

    The machine verifies what a machine can. I review what is left: naming, trade-offs, and the thing the checks do not know to look for.

Six rules I work by

Each of these came out of something I built. The tags point to the artifact where you can see it.

  1. Context is the real prompt

    Most bad output is a context problem. The model did not know what was true, what was allowed, or what good looks like. So that is where my effort goes: vetted sources, explicit scope, and the smallest set of files that makes the task unambiguous. Clever wording comes a distant second.

    In practice. My diagram agent does not answer domain questions from memory. It first searches a private index of reference documents I chose, and the web, and only then commits to a diagram. artifact A-05

  2. Put the feedback in the tool, not the prompt

    Asking a model to “avoid overlapping boxes” is a wish. Handing it the list of boxes that overlap is a loop. Agents get better when their tools report consequences, because evidence in the context beats instructions about the future.

    In practice. In my diagram agent, every call that adds elements returns the pairs that now collide, and the agent repairs them before it finishes. artifact A-05

  3. Evals are the contract

    If I cannot measure it, I cannot tell an improvement from a change. Model behaviour gets a golden dataset and scorers, structural ones first: do the arrows attach, do the labels bind, did it call the right tool in the right order. A prompt tweak has to earn its place against the last run.

    In practice. A 30-case golden dataset and eight scorers, with every run recorded as an experiment tagged with its commit. artifact A-05

  4. Grade what actually runs

    An eval that exercises a copy of the system proves the copy works. The harness has to import the same prompt, the same tools and the same checks as production, or the numbers are decoration.

    In practice. The eval harness shares the system prompt and the overlap detector with the deployed agent, and simulates the canvas so it can run without a browser. artifact A-05

  5. Make bad output unrepresentable

    Constraints do more than instructions. Types, strict schemas and narrow interfaces shrink the space of things a model can get wrong, which is cheaper than catching mistakes afterwards.

    In practice. The agent’s tool inputs are Zod schemas in strict mode with nullable fields instead of optional ones, so a malformed tool call is not something the model can produce. artifact A-05

  6. Verify against the real thing, and fail loudly

    “It should work” is not a status. I want the check that runs against the real server, the real browser, the real build. And when a guarantee cannot be met, I want the system to stop, not to carry on quietly without it.

    In practice. The ticket booth’s Redis store is tested against real Redis servers and a 45-check browser suite, and it refuses to fall back silently when Redis is unreachable. artifact A-04

Where I do not hand over the wheel

  • Decisions with a long tail. Data models, public interfaces, what to cache and what never to. A model is good at laying out options. Choosing is my job, because I am the one who lives with it.
  • Anything I cannot explain. If I cannot walk through a change line by line, it does not merge.
  • Secrets and private data. They stay out of prompts.
  • Irreversible actions. Publishing, deleting, sending: those wait for a human yes.

What a team gets

Speed with a safety net. I move quickly with these tools because the checks are in place first, and I can set the same things up for a team: a golden dataset and scorers for an AI feature, strict schemas around tool calls, verification scripts that run against a real build.

I have also mentored junior developers, so I care about how a team learns to use these tools, not only whether I can.
